## Purpose

Defines the integration test suite that measures the route algorithm against the real France graphs and the real tariffs, the committed file of expected values it compares against, and how that file is regenerated when the pipeline is rebuilt.

## ADDED Requirements

### Requirement: The suite runs against the real graphs from inside the Compose network

The suite SHALL query the same two services the application queries, `osrm-toll` and `osrm-optimal`, over the Compose network, and SHALL read the same four pipeline artefacts.

It SHALL NOT stand up a fake router, and SHALL NOT reach the routers through a published host port. On this host the published ports refuse connections while the same query over the Compose network succeeds, so a suite that used them would report the whole algorithm as broken.

A run SHALL fail with a clear message, rather than with a connection error per test, when a router is not answering or an artefact is missing.

#### Scenario: The suite is invoked

- **WHEN** the test runner service is started
- **THEN** it joins the Compose network, reaches both routers by name, and runs against the France graphs

#### Scenario: A router is down

- **WHEN** `osrm-optimal` is not running
- **THEN** the run stops with one message naming that service

### Requirement: Expected values are exact and committed

A committed fixture file SHALL hold, for each test journey, the values a correct run produces:

- the origin and the destination, as `[longitude, latitude]`;
- for each of the two routes: its distance in metres, its duration in seconds, its node count, and a digest of its node id sequence;
- for each of the two routes: every passage in driven order, with its name and its cost, and the total;
- for the optimal route: every waypoint coordinate, the number of waypoints needed, whether the link is complete, and the divergences;
- the number of unpriced passages and the reason of each.

A digest stands in for the node id sequence because a Lyon–Paris route has 6 945 of them. It is exact — any change to the driven road changes it — and it is one line.

Comparison SHALL be exact. Distances, durations, and costs SHALL match to the precision the fixture records.

#### Scenario: A changed road is caught

- **WHEN** the optimal route drives one different node
- **THEN** its node id digest differs from the fixture and the test fails

#### Scenario: A changed tariff is caught

- **WHEN** a passage that cost 13.70 EUR now costs 14.10 EUR
- **THEN** the test fails naming that passage, its expected cost, and its actual cost

### Requirement: The fixture is stamped with the data it was generated against

The fixture SHALL carry the data fingerprint — the same fingerprint the service uses as part of its cache key — of the artefacts it was generated against.

When the live fingerprint differs from the fixture's, the suite SHALL stop with one message saying the pipeline has been rebuilt and naming the command that regenerates the fixture. It SHALL NOT report every journey as a failure.

Exact expected values against a rebuilt France extract fail for the reason the extract changed, not for the reason the algorithm changed. Without the stamp, a rebuild produces a wall of mismatches that says nothing about the code, and the habit that follows is to regenerate without reading them.

#### Scenario: The pipeline was rebuilt

- **WHEN** the artefacts have changed since the fixture was generated
- **THEN** the run stops with one message naming the regeneration command, and no journey is reported as a failure

#### Scenario: The pipeline is unchanged

- **WHEN** the fingerprints agree
- **THEN** every journey is compared against its expected values

### Requirement: The fixture is regenerated by a documented command

One documented command SHALL rewrite the fixture from a live run and stamp it with the current fingerprint.

The command SHALL print a diff of what changed against the previous fixture, so the operator reads what the rebuild moved before committing it. It SHALL NOT run as part of an ordinary test run.

#### Scenario: Regeneration reports what moved

- **WHEN** the fixture is regenerated after a pipeline rebuild
- **THEN** the command prints, per journey, the values that changed and by how much

#### Scenario: An ordinary run never rewrites the fixture

- **WHEN** the suite runs and a journey fails
- **THEN** the fixture on disk is unchanged

### Requirement: The journeys cover every accounting path

The fixture SHALL hold at least one journey for each of:

- a journey with no toll at all, where both routes are the same and no waypoint is emitted;
- a long journey where the two routes differ and several waypoints are emitted — Lyon to Paris, where the fast route is about 465 km and the optimal about 505 km;
- a journey crossing a `passthrough` barrier;
- a journey crossing a `gantry`, which the model this suite replaces could not charge;
- a journey crossing a `bidirectional` barrier from the outside, so it opens a ticket;
- the same journey reversed, crossing that barrier from the inside, so it closes one;
- a journey beginning inside the toll network, so its first passage is an exit with no entrance and is recorded unpriced;
- a journey ending inside the toll network, so a ticket is left open and recorded unpriced;
- a journey crossing a plaza whose lane the router picks is recorded as an alias, so the passage is charged against the plaza.

Each SHALL assert the passages by name and cost, not only the total. A total can be right while two passages are wrong.

#### Scenario: The two directions of a two-way barrier disagree

- **WHEN** the two `bidirectional` journeys are compared
- **THEN** one opens a ticket at that barrier and the other closes one, and their passage lists differ accordingly

#### Scenario: A gantry appears in the passages

- **WHEN** the gantry journey is run
- **THEN** its passage list names the gantry and charges its price

### Requirement: Every journey is checked against the invariants as well

Beyond the recorded values, each journey SHALL be checked against properties that hold whatever the graph says:

- every waypoint coordinate is a coordinate of the optimal route;
- re-querying each leg between consecutive waypoints on the untouched graph reproduces the optimal route's node sequence for that stretch;
- each waypoint coordinate, snapped without a hint, lands on a segment of the optimal route;
- the optimal route's duration is not less than the fast route's, since the segment weight file preserves duration and the fast route is the time minimum;
- the passages of a route appear in the order the route's node sequence reaches them.

These hold across a pipeline rebuild. They are what still tests the algorithm on the day the recorded values have to be regenerated.

#### Scenario: A waypoint off the route is caught

- **WHEN** an emitted waypoint is not a coordinate of the optimal route
- **THEN** the invariant fails, whatever the fixture records

#### Scenario: A leg that does not reproduce the route is caught

- **WHEN** the untouched graph's route between two consecutive waypoints differs from the optimal route between them
- **THEN** the invariant fails

### Requirement: The bounds are tested by setting them, not by finding a journey that reaches them

The waypoint cap, the query budget, and the reach SHALL be tested by running a real journey with the bound lowered.

Hunting for a French journey that naturally needs ten waypoints ties the test to the extract, and the journey stops needing ten the next time the graph is built. Lowering the cap to two on a journey that needs four tests the same code and holds.

#### Scenario: The cap is reached

- **WHEN** a journey needing four waypoints is run with the cap set to two
- **THEN** two waypoints are returned, `waypoints_needed` is 4, and the link is marked incomplete

#### Scenario: The budget is reached

- **WHEN** a long journey is run with the query budget set below what it needs
- **THEN** the verified waypoints are returned and the link is marked incomplete, and nothing is raised

#### Scenario: The reach is exceeded

- **WHEN** an origin is submitted with the reach set below its distance to the network
- **THEN** the query fails naming the measured distance

### Requirement: A failing test names the journey and the difference

A failure SHALL name the journey, the field, the expected value, and the actual value. Where a passage list differs, it SHALL show the passages that differ rather than two whole lists.

#### Scenario: A passage list differs by one entry

- **WHEN** one passage of a nine-passage journey has a different cost
- **THEN** the failure names that passage, its expected cost, and its actual cost, and does not print the other eight
